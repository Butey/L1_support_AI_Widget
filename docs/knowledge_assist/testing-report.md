# Support AI Assistant — Testing Report

## 1. Назначение

Модуль определяет структуру отчёта о тестировании SmartCore.

Отчёт должен позволить понять:

- что проверялось;
- какими тестами;
- какие тесты были изменены или созданы;
- какие проверки пройдены;
- какие проверки провалены;
- какие дефекты обнаружены;
- какие ограничения остались;
- каков итог тестирования.

---

# 2. Источники отчёта

Отчёт формируется только по фактически выполненным проверкам.

Источниками являются:

- тест-план;
- тест-кейсы;
- результаты выполнения;
- багрепорты;
- задачи;
- Merge Requests;
- чек-листы.

Не отмечать тест как PASSED без результата выполнения.

---

# 3. Merge Requests

Внутренний шаблон предусматривает ссылку на Merge Requests для новых тест-кейсов.

Указывать:

`[Merge Requests](ссылка)`

если новые или изменённые тест-кейсы действительно оформлялись через MR.

---

# 4. Errata

Для HRDW внутренний шаблон предусматривает отдельную ссылку на кейсы Errata.

Использовать только для HRDW, когда применимо.

---

# 5. Багрепорты

Можно указать:

- список найденных багов;
- связанные задачи;
- backlog.

Не дублировать полный текст багрепортов в отчёте, если достаточно ссылок.

---

# 6. Основная таблица

Использовать:

| № | Пункт проверки | Тест-кейс | Изменения | Результат |
|---|---|---|---|---|
| 1 | ... | ... | существующий / новый / доработка | PASSED / FAILED |
| 2 | ... | ... | существующий / новый / доработка | PASSED / FAILED |

Поле «Изменения» показывает состояние тестовой документации:

- существующий;
- новый;
- доработка.

---

# 7. Результаты

Использовать как минимум:

`PASSED`

`FAILED`

Не ставить PASSED, если проверка:

- не выполнялась;
- заблокирована;
- не завершена.

Если внутренний процесс допускает дополнительные статусы, использовать только подтверждённые статусы.

---

# 8. FAILED

Для FAILED должна существовать возможность понять причину.

Указать:

- багрепорт;
- задачу;
- краткое описание;
- блокирующую зависимость.

Не превращать таблицу отчёта в полный багрепорт.

---

# 9. Чек-лист

Если использовался чек-лист:

`[Чек-лист проверок](ссылка)`

Если чек-лист не использовался, не добавлять фиктивную ссылку.

---

# 10. Итог

Итог должен быть основан на результатах.

Он может содержать:

- количество выполненных проверок;
- количество PASSED;
- количество FAILED;
- найденные блокирующие проблемы;
- известные ограничения;
- непроверенные области.

Не использовать общий вывод:

> Всё работает.

если тестирование не покрывало весь продукт.

---

# 11. Границы тестирования

При необходимости явно указать:

## Не проверялось

- ...

## Ограничения

- ...

## Заблокировано

- ...

Это предотвращает интерпретацию частичной проверки как полной.

---

# 12. Новая тестовая документация

Если во время тестирования были созданы новые кейсы:

- указать MR;
- указать новые тест-кейсы;
- указать причину создания.

Если существующие кейсы изменены:

- указать доработанные кейсы;
- указать MR.

# 14. Правила итогового заключения

Заключение должно точно соответствовать объёму тестирования.

Если все выполненные проверки PASSED:

> Все проверки, предусмотренные данным тест-планом, пройдены успешно.

Это не означает:

> В продукте нет ошибок.

Если существуют FAILED:

> По результатам тестирования обнаружены дефекты. См. связанные багрепорты.

Если часть тестирования заблокирована:

> Тестирование завершено частично. Перечисленные проверки не выполнены из-за указанных ограничений.

---

# 15. Контроль качества

Перед формированием отчёта проверить:

- каждый ли результат подтверждён выполненной проверкой;
- есть ли ссылки на тест-кейсы;
- связаны ли FAILED с дефектами;
- отмечены ли новые/изменённые тест-кейсы;
- указаны ли ограничения;
- не сделан ли вывод шире фактического покрытия;
- не выданы ли непроверенные функции за работающие.
