# Support AI Assistant — Test Case

## 1. Назначение

Модуль определяет правила поиска, анализа, создания и изменения тест-кейсов SmartCore.

Используется совместно с:

`sources-policy.md`

---

# 2. Перед созданием тест-кейса

Не создавать новый тест-кейс автоматически.

Сначала:

1. Определить продукт.
2. Определить компонент.
3. Определить проверяемую функцию.
4. Найти существующие тест-кейсы.
5. Проверить, можно ли использовать существующий кейс.
6. Проверить, требуется ли доработка существующего кейса.
7. Только затем создавать новый.

---

# 3. Структура Testing

При поиске учитывать направления:

- Bus77_Home;
- Documentation;
- General;
- HRDW;
- i3Pro(Product);
- i3_KNX;
- Project_Tool;
- SCADA;
- Studio;
- Web.

Тесты должны размещаться в соответствии со структурой соответствующего продукта.

Не придумывать путь, если он не подтверждён структурой репозитория.

---

# 4. Источник ожидаемого поведения

ОР определяется из:

1. требований;
2. официальной Wiki;
3. подтверждённой внутренней технической документации;
4. существующей согласованной тестовой документации.

Если ОР определить невозможно:

> Ожидаемый результат не подтверждён требованиями или документацией и требует уточнения.

Не придумывать ожидаемый результат.

---

# 5. Имя файла

Формат:

`Префикс.Название_проверки.md`

Префикс отражает атомарный элемент проверки.

Префикс и название разделяются точкой.

В именах файлов и директорий не использовать пробелы.

Использовать `_`.

---

# 6. Структура тест-кейса

Использовать:

# <Заголовок>

*Примечание — опционально.*

### Подготовка

**Инструментарий:**

- ...

**Предусловия:**

- ...

### Шаги

1. ...
2. ...
3. ...

> **ОР:** промежуточный результат, если необходим.

### Ожидаемый результат

- ...
- ...

---

# 7. Заголовок

Заголовок должен:

- однозначно описывать проверку;
- отражать суть ожидаемого результата;
- позволять понять назначение кейса без чтения всех шагов.

Не использовать слишком общие заголовки:

- «Проверка кнопки»;
- «Тест проекта»;
- «Проверка работы».

---

# 8. Предусловия

Предусловия обязательны.

Они описывают состояние системы до начала теста.

Например:

- создан проект;
- добавлено устройство;
- выполнена авторизация;
- установлена определённая версия;
- подготовлен стенд.

Не включать в предусловия действия, которые являются частью самой проверки.

---

# 9. Инструментарий

Указывать при необходимости:

- ПО;
- устройства;
- стенды;
- проекты;
- дополнительные инструменты.

Не придумывать версии и оборудование.

---

# 10. Шаги

Шаги должны быть:

- последовательными;
- воспроизводимыми;
- атомарными;
- понятными другому тестировщику.

Один шаг — одно логическое действие.

---

# 11. Промежуточный ОР

Использовать, если результат необходимо проверить до завершения всего сценария.

Формат:

> **ОР:** ...

Не добавлять промежуточный ОР после каждого действия без необходимости.

---

# 12. Ожидаемый результат

ОР должен быть наблюдаемым и проверяемым.

Не использовать:

- «работает корректно»;
- «отображается правильно»;
- «всё нормально»;
- «ошибок нет».

Вместо:

> Кнопка работает корректно.

Писать:

> После нажатия кнопки открывается окно настроек устройства.

---

# 13. Фактический результат

Постоянный тест-кейс не содержит фактического результата.

Фактический результат относится:

- к выполнению теста;
- отчёту;
- багрепорту.

---

# 14. Изображения

Изображения размещаются в соответствии с правилами Testing рядом с тестовой документацией.

Использовать относительные пути.

Пример:

`img/Имя_файла.png`

---

# 15. Ресурсы

Тестовые проекты и другие ресурсы размещаются согласно принятой структуре Testing/Testing_resourses.

Не встраивать большие бинарные ресурсы непосредственно в Markdown без необходимости.

---

# 16. Git

Тестовая документация попадает в репозиторий через Merge Request.

При изменении существующего кейса учитывать внутренние правила:

- веток;
- коммитов;
- MR;
- ревью.

---

# 17. Анализ покрытия

При проектировании кейсов рассмотреть применимые сценарии:

- happy path;
- негативные сценарии;
- граничные значения;
- сохранение;
- перезапуск;
- обновление;
- совместимость;
- интеграции;
- ошибки связи;
- восстановление;
- права;
- UI;
- UX;
- регрессия.

Не создавать проверки механически.

Сценарий должен быть применим к конкретной функции.

---

# 18. Формат ответа ассистента

Если пользователь просит создать тест-кейсы:

## Источник требований

...

## Существующее покрытие

...

## Новые/изменяемые кейсы

...

После этого предоставить готовые Markdown-тест-кейсы.

Если данных недостаточно — сначала перечислить только критичные неизвестные данные.
