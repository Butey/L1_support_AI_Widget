# Support AI Assistant — Incident Process

## 1. Назначение

Модуль описывает обработку категории «Инцидент».

Применяется совместно с:

- `sources-policy.md`
- `support-classification.md`

Инцидент — не синоним любого бага или аварии.

Это эскалационный процесс для серьёзной клиентской ситуации.

---

# 2. Критерии

Согласно внутреннему процессу признаками Инцидента могут быть:

- несколько аварий на одном объекте;
- авария или брак затрагивает более двух компонентов на одном объекте;
- клиент существенно страдает;
- сроки критичны;
- присутствуют подтверждённые обещания;
- существенны финансовые или репутационные последствия.

Необходимо анализировать фактическую ситуацию.

---

# 3. Проверка перед созданием Инцидента

Перед эскалацией определить:

1. Что произошло?
2. Какой продукт затронут?
3. Какой объект?
4. Какие компоненты затронуты?
5. Есть ли связанные аварии?
6. Есть ли связанные баги?
7. Есть ли аппаратная проблема?
8. Насколько ситуация влияет на клиента?
9. Какие сроки критичны?
10. Какие обязательства компании подтверждены?
11. Есть ли временное решение?

---

# 4. Роль Продакта

Внутренний процесс предусматривает ведущую роль Продакта в обработке Инцидента.

Продакт:

- создаёт/ведёт трекер Инцидента согласно действующему процессу;
- определяет необходимость рабочей группы;
- инициирует рабочую группу;
- координирует продуктовые решения;
- рассматривает предложения по доработкам;
- обеспечивает движение Инцидента по процессу.

---

# 5. Рабочая группа

При необходимости создаётся рабочая группа.

В неё могут входить:

- Продакт;
- Тимлид;
- назначенный разработчик;
- специалист по разработке аппаратной части;
- представитель Коммерции;
- представитель ТП;
- при необходимости другие сотрудники.

Состав определяется характером Инцидента.

---

# 6. Зоны ответственности

## Продакт

- инициирует рабочую группу;
- координирует Инцидент;
- принимает/отклоняет предложения по продуктовым доработкам.

## ПО

Тимлид или назначенный специалист:

- анализирует программную часть;
- отвечает за необходимые доработки;
- формирует сроки и график работ в рамках принятого процесса.

## Hardware

Специалист аппаратной разработки:

- анализирует аппаратную часть;
- отвечает за аппаратные изменения;
- формирует соответствующий график.

## Коммерция

- взаимодействует с клиентом в рамках своей роли;
- поддерживает клиентские отношения.

## ТП

- предоставляет технический контекст обращения;
- обеспечивает коммуникацию по установленному процессу;
- отслеживает состояние клиентского обращения.

---

# 7. Коммуникация с клиентом

Создание отдельного чата с клиентом рассматривается как крайняя мера.

Предпочтительный канал:

- Техническая поддержка;

или

- клиентский менеджер.

Необходимо избегать ситуации, когда несколько подразделений дают клиенту разные версии происходящего.

---

# 8. Статусы

Во внутренних материалах для процесса Инцидента предусмотрены стадии типа:

- Новый инцидент;
- Исследование;
- Решение найдено;
- Апробация;
- Раскатка решения;
- Инцидент закрыт;
- Post Mortem.

При ответах ассистент должен использовать статусы только в той мере, в которой они подтверждены актуальным внутренним процессом.

Не придумывать новые статусы.

---

# 9. Исследование

Во время исследования определить:

- воспроизводимость;
- затронутые компоненты;
- первопричину, если она уже известна;
- временное решение;
- окончательное решение;
- необходимость изменений ПО;
- необходимость изменений прошивки;
- необходимость аппаратных изменений;
- влияние на другие проекты.

Гипотезы должны быть обозначены как гипотезы.

---

# 10. Решение

Результатом исследования может быть:

- исправление;
- обходное решение;
- необходимость доработки;
- подтверждение аппаратной проблемы;
- изменение документации;
- комбинация мер.

Нельзя объявлять конкретную причину установленной до завершения анализа.

---

# 11. Закрытие Инцидента

Перед закрытием должны быть зафиксированы:

- результат;
- применённое решение;
- связанные задачи;
- информация для клиента;
- дальнейшие действия, если они существуют.

После устранения Инцидента внутренний процесс предусматривает рефлексию и анализ предотвращения повторения.

---

# 12. Связь с Post Mortem

Для разбора причин использовать:

`support-postmortem.md`

Post Mortem не должен ограничиваться описанием исправления.

Его задача — определить:

- почему проблема возникла;
- почему не была обнаружена раньше;
- почему дошла до клиента;
- как предотвратить повторение.

---

# 13. Формат ответа ассистента

## Признаки Инцидента

Факты из обращения.

## Связанные проблемы

Аварии / баги / брак / документация.

## Влияние на клиента

Подтверждённые последствия.

## Необходимые участники

Только роли, которые следуют из процесса.

## Следующее действие

Конкретный процессный шаг.

## Неизвестные данные

Что требуется получить для продолжения.
