### 1. Интеграция скилла `support-escalation` и генерация заметок в Omnidesk
* **Контекст задачи:**  
  Необходимо было связать работу скилла `support-escalation` с реальным интерфейсом Omnidesk: если ИИ определяет необходимость эскалации тикета в смежный отдел (разработка, сервис, пресейл, продажи), он должен автоматически формировать внутреннюю заметку для сотрудников.
* **Итерация и корректировка (Сценарий А):**  
  Первоначальная логика генерировала заметку при каждом ответе виджета. По требованию пользователя была внедрена строгая фильтрация (Сценарий А): заметка создается и отправляется в Omnidesk **только тогда, когда эскалация действительно необходима**.
* **Что было изменено в системных инструкциях для LLM ([`server.ts:2253-2268`](file:///opt/webapps/omniai/gemini_omni/server.ts#L2253-L2268), исполнение в [`server.ts:2642-2720`](file:///opt/webapps/omniai/gemini_omni/server.ts#L2642-L2720)):**
  - В системный мастер-промпт внедрен структурированный блок инструкций для скилла `support-escalation`:
    ```json
    "escalation": {
      "used": true/false,
      "required": true/false,
      "note_content": "СТРОГО пусто (\"\"), если required=false. Если required=true — внутренний комментарий для Omnidesk по разделам 'Что есть' и 'Чего не хватает'."
    }
    ```
  - Закреплено жесткое требование: если проблема решается силами 1-й линии техподдержки, `required` обязан быть `false`, а `note_content` — пустой строкой `""`.
* **Что было изменено в бэкенде и API:**
  - Реализована функция `addOmnideskNote(caseId, noteContent, staffEmail)` с дедупликационным кэшем `recentNotesCache` (защита от повторного создания одинаковых заметок при повторных запросах).
  - Эндпоинт `POST /api/cases/{case_id}/notes.json` вызывается только при `escalation.required === true`.
* **Что было изменено в интерфейсе виджета ([`WidgetPreview.tsx`](file:///opt/webapps/omniai/gemini_omni/src/components/WidgetPreview.tsx)):**
  - Добавлен визуальный бейдж эскалации с отображением подготовленной заметки («Что есть» / «Чего не хватает») только при подтвержденной эскалации.
* **Тестирование:**
  - Написан интеграционный тест [`test/escalation_note.test.ts`](file:///opt/webapps/omniai/gemini_omni/test/escalation_note.test.ts), проверяющий отправку заметок строго по Сценарию А.

### 8. Прямая маршрутизация тикетов со скриншотами на `gemini-3.5-flash-lite` и устранение задержек
* **Контекст задачи:**  
  При обработке тикетов с прикрепленными скриншотами виджет по умолчанию использовал тяжелую модель из настроек (`gemini-3.8-flash`). Мультимодальные запросы быстро упирались в лимиты квот (HTTP 429), и каскадный переход `3.8-flash` → `3.7-flash` → `3.6-flash` → `3.5-flash` занимал более 100 секунд до успешного ответа на `3.5-flash-lite`.
* **Исследование моделей:**
  - Проверена модель `gemma-4-31b-it`: API Google GenAI возвращает ошибку (`Only text input is supported for this model`). Модели семейства Gemma не поддерживают входящие изображения.
  - Легковесным мультимодальным решением с максимальной скоростью и высокими квотами является `gemini-3.5-flash-lite` (и `gemini-3.1-flash-lite`).
* **Что было внедрено:**
  - В `server.ts` реализована функция `selectModelForRequest(baseModel, hasImages, isCustom)`: при `hasImages = true` запрос сразу адресуется модели `gemini-3.5-flash-lite` (или `gemini-3.1-flash-lite`), минуя тяжелые модели.
  - Чисто текстовые тикеты продолжают использовать базовую модель из настроек админки (`settings.model_name`).
  - Внедрена специализированная цепочка `IMAGE_MODEL_FALLBACK_CHAIN`:
    `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite` → `gemini-3.5-flash` → `gemini-3.6-flash` → `gemini-3.7-flash` → `gemini-3.8-flash`.
  - Время генерации ответа виджета на тикеты со скриншотами сократилось со 105+ секунд до ~1.5–3 секунд.
* **Тестирование:**
  - Дополнен тестовый сьют `test/image_recognition.test.ts` проверками маршрутизации и fallback для изображений (8 тестов в сьюте).
  - Все **60 тестов в 13 сьютах проходят успешно (100% pass)**.

### 9. Дедупликация и персистентное кэширование распознанных изображений (18 сентября 2026)
* **Контекст задачи:**  
  При каждом обращении оператора к виджету (первый ответ, уточняющие вопросы в чате тикета, генерация черновиков) `server.ts` повторно скачивал изображения из тикета и передавал их в Base64 в vision-модель. Требовалось исключить повторное распознавание и сетевые загрузки уже проанализированных изображений.
* **Что было внедрено:**
  - **Двухуровневый кэш `storage/recognized_images.json`**:
    - Персистентный файл `storage/recognized_images.json` сохраняет записи между перезапусками Docker.
    - В памяти поддерживается `recognizedImagesCache = new Map<string, RecognizedImageRecord>()` с 4 вторичными индексами: по Omnidesk `file_id`, URL вложения, SHA-256 хешу содержимого и составному ключу `caseNumber + fileName + fileSize`.
    - Функции `findInRecognizedCache`, `recordRecognizedImage`, `loadRecognizedImages`, `saveRecognizedImages`.
  - **Оптимизация потока в `/api/chat`**:
    - Вложения тикета разделяются на `alreadyRecognizedImages` (найденные в кэше) и `unrecognizedAttachments` (новые).
    - Закэшированные изображения **не скачиваются** по сети! Их извлеченное текстовое описание (`visualDescription`) подставляется прямо в промпт модели в блок `Ранее распознанные изображения из тикета`.
    - Скачиваются только новые изображения. Для каждого скачанного файла вычисляется SHA-256 хеш; если хеш уже есть в кэше, изображение переносится в закэшированные.
    - Если все изображения тикета уже распознаны (`loadedImages.length === 0`), запрос мгновенно адресуется базовой текстовой модели (`settings.model_name`, например `gemini-3.8-flash`), минуя vision rate limits и лишние токены.
    - После успешного ответа модели описания извлекаются из поля `image_descriptions` ответа (с fallback на `reply`) и атомарно сохраняются на диск.
  - **Интерфейс виджета (`WidgetPreview.tsx`)**:
    - Бейдж `🖼️ Проанализировано N изображений` показывается только при наличии новых картинок.
    - Для закэшированных картинок выводится статус `💾 Использовано N изображений из кэша`.
* **Тестирование:**
  - Написано 4 новых модульных теста в `test/image_recognition.test.ts` (поиск по ключам/хешам, отмена повторной загрузки, выбор текстовой модели при отсутствии новых картинок, персистентность кэша).
  - Все **64 теста в 13 сьютах проходят успешно (100% pass)**.
