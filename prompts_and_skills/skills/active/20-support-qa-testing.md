# QA-тестирование SmartPlatform: стандарты и шаблоны

## Часть 1. Тест-кейс

### 1.1 Перед созданием тест-кейса

**Не создавать новый тест-кейс автоматически.** Сначала:

1. Определить продукт.
2. Определить компонент.
3. Определить проверяемую функцию.
4. Найти существующие тест-кейсы в репозитории.
5. Проверить, можно ли использовать существующий кейс.
6. Проверить, требуется ли доработка существующего кейса.
7. Только затем создавать новый.

### 1.2 Структура репозитория Testing SmartPlatform

При поиске и размещении тест-кейсов учитывать направления:

- `Bus77_Home` — Home Automation на шине Bus77;
- `Documentation` — тесты документации;
- `General` — общие сценарии;
- `HRDW` — аппаратное обеспечение SmartPlatform;
- `i3Pro(Product)` — i3 Pro продуктовые сценарии;
- `i3_KNX` — интеграция KNX;
- `Project_Tool` — Studio IDE / Project Tool;
- `SCADA` — SCADA и BMS;
- `Studio` — Studio IDE;
- `Web` — Web-интерфейсы.

Не придумывать путь, если он не подтверждён структурой репозитория.

### 1.3 Источник ожидаемого поведения (ОР)

ОР определяется из:

1. официальных требований;
2. официальной Wiki (`docs.example.com`, `dev.example.com`, `scada.example.com/scada`);
3. подтверждённой внутренней технической документации;
4. существующей согласованной тестовой документации.

Если ОР определить невозможно:

> Ожидаемый результат не подтверждён требованиями или документацией и требует уточнения.

### 1.4 Имя файла

Формат: `Префикс.Название_проверки.md`

- Префикс отражает атомарный элемент проверки.
- Префикс и название разделяются точкой.
- Не использовать пробелы. Использовать `_`.

Пример: `Login.Auth_by_email.md`, `KNX.Group_address_write.md`

### 1.5 Шаблон тест-кейса

```markdown
# <Заголовок — однозначно описывает проверку и отражает ОР>

*Примечание:* <опционально>

### Подготовка

**Инструментарий:**

- <ПО, оборудование, версии>

**Предусловия:**

- <состояние системы до теста>
- <авторизация, подготовленный стенд, версия>

### Шаги

1. <действие>
2. <действие>
3. <действие>

> **ОР:** <промежуточный результат, если необходим>

### Ожидаемый результат

- <конкретное наблюдаемое поведение>
- <не «всё работает», а «значение сохраняется и отображается после повторного открытия»>
```

**Правила заголовка:**
- Не использовать общие заголовки: «Проверка кнопки», «Тест проекта», «Проверка работы».
- Хороший заголовок: «KNX: запись в группу адресов с панели i3 Pro сохраняется на шине».

**Правила предусловий:**
- Описывают состояние системы ДО начала теста.
- Не включать в предусловия действия, которые являются частью самой проверки.

## Часть 2. Тест-план

### 2.1 Источники перед созданием

Изучить:

1. задачу/требования/описание изменения;
2. официальную Wiki;
3. существующие тест-кейсы;
4. существующие чек-листы;
5. связанные баги;
6. изменяемые компоненты.

Не придумывать область изменений без источника.

### 2.2 Шаблон тест-плана

```markdown
# Тест-план: <название задачи / релиза / фичи>
```

## Часть 3. Отчёт о тестировании

### 3.1 Правила

- Отчёт формируется только по **фактически выполненным** проверкам.
- Не отмечать тест как PASSED без результата выполнения.
- Не ставить PASSED, если проверка не выполнялась, заблокирована или не завершена.

### 3.2 Шаблон отчёта

```markdown
# Отчёт о тестировании: <название>

**Версия / задача:** <значение>
**Дата:** <значение>
**Тестировщик:** <значение>

**Merge Requests (новые/изменённые тест-кейсы):**

- <список найденных багов или «не обнаружено»>
```
