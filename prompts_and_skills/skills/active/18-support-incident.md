# Процесс обработки Инцидента

> **Инцидент — не синоним любого бага или аварии. Это эскалационный процесс для серьёзной клиентской ситуации.**

## 1. Критерии квалификации

Признаки Инцидента (один или несколько):

- несколько аварий на одном объекте;
- авария или брак затрагивает **более двух компонентов** на одном объекте;
- клиент существенно страдает (финансовые потери, репутационные риски, остановка производства);
- **сроки критичны** (сдача объекта, публичное мероприятие, договорные обязательства);
- присутствуют **подтверждённые обещания** компании клиенту;
- существенны финансовые или репутационные последствия.

Необходимо анализировать фактическую ситуацию, а не только формулировку обращения.

## 2. Проверочный список перед созданием Инцидента

Перед эскалацией определить и зафиксировать:

1. Что произошло?
2. Какой продукт затронут?
3. Какой объект?
4. Какие компоненты затронуты?
5. Есть ли связанные аварии?
6. Есть ли связанные баги?
7. Есть ли аппаратная проблема?
8. Насколько ситуация влияет на клиента?
9. Какие сроки критичны и подтверждены?
10. Какие обязательства компании подтверждены?
11. Есть ли временное решение (workaround)?

## 3. Роль Продакта

Внутренний процесс предусматривает **ведущую роль Продакта** в обработке Инцидента.

Продакт:

- создаёт и ведёт трекер Инцидента;
- определяет необходимость рабочей группы;
- инициирует рабочую группу;
- координирует продуктовые решения;
- рассматривает предложения по доработкам;
- обеспечивает движение Инцидента по процессу.

## 4. Рабочая группа

При необходимости создаётся рабочая группа. Состав определяется характером Инцидента:

| Участник | Зона ответственности |
|---|---|
| **Продакт** | Инициирует РГ, координирует Инцидент, принимает/отклоняет продуктовые решения |
| **Тимлид / разработчик ПО** | Анализирует программную часть, отвечает за доработки, формирует сроки |
| **Hardware-специалист** | Анализирует аппаратную часть, отвечает за аппаратные изменения |
| **Коммерция** | Взаимодействует с клиентом в рамках своей роли, поддерживает клиентские отношения |
| **ТП** | Предоставляет технический контекст, обеспечивает коммуникацию, отслеживает обращение |
| Другие сотрудники | По необходимости |

## 5. Коммуникация с клиентом

**Правило единого окна:** Создание отдельного чата с клиентом рассматривается как **крайняя мера**.

Предпочтительный канал:

- Техническая поддержка (основной);
- клиентский менеджер (если ТП недоступна или клиент настаивает).

Необходимо избегать ситуации, когда несколько подразделений дают клиенту **разные версии** происходящего.

## 6. Жизненный цикл и статусы

| Статус | Описание |
|---|---|
| Новый инцидент | Зафиксирован, ждёт первичной оценки |
| Исследование | Рабочая группа анализирует причины и масштаб |
| Решение найдено | Определён и согласован план устранения |
| Апробация | Решение проверяется |
| Раскатка решения | Решение доставляется клиенту |
| Инцидент закрыт | Проблема устранена, клиент подтвердил |
| Post Mortem | Анализ причин и превентивные меры (подключи `support-postmortem`) |
