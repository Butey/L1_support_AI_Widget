# Post Mortem SmartPlatform

> **Главная задача:** Не только описать, как исправили проблему, но определить **причины возникновения**, **причины позднего обнаружения** и **действия, предотвращающие повторение**.

Post Mortem должен основываться на **фактах**. Гипотезы необходимо явно отделять от установленных причин.

## 1. Исходные данные (собрать перед формированием)

- Описание проблемы:
- Продукт / компонент / версии:
- Объект (клиент):
- Дата и время обнаружения:
- Источник обнаружения (клиент, мониторинг, сотрудник):
- Шаги воспроизведения:
- Логи и скриншоты:
- Связанные задачи / тикеты:
- Временные решения:
- Окончательное решение:
- Участники расследования:

## 2. Корневая причина

Ответить: **Что непосредственно привело к аварии?**

Указать установленную корневую причину.

Если причина ещё не доказана:

> Корневая причина не подтверждена. Наиболее вероятная гипотеза: `<гипотеза>`.

Не превращать наиболее вероятную гипотезу в факт.

## 3. Диаграмма Исикавы (анализ категорий)

При анализе рассмотреть применимые категории. Заполнять только при наличии фактов — не нужно искусственно заполнять каждую категорию.

### Люди
- ошибки коммуникации;
- недостаток знаний или компетенций;
- отсутствие необходимого участника;
- неправильная передача информации.

### Процессы
- недостатки ревью;
- недостатки тестирования;
- пробелы процесса разработки или выпуска;
- пробелы передачи информации.

### Инструменты
- отсутствие автоматизации;
- недостаточный мониторинг;
- проблемы CI/CD;
- недостаточная диагностика.

### Код
- дефекты;
- регрессии;
- неправильная обработка состояния;
- ошибки совместимости.

### Инфраструктура
- серверы;
- сеть;
- окружение;
- конфигурация;
- внешние зависимости.

## 4. Timeline (хронология)

Восстановить последовательность событий на основе **фактических данных из тикетов и систем**:

| № | Событие | Дата и время |
|---|---|---|
| 1 | Когда проблема появилась? | |
| 2 | Когда её обнаружили? | |
| 3 | Кто обнаружил? | |
| 4 | Когда она попала в ТП? | |
| 5 | Когда создана авария/тикет? | |
| 6 | Когда началось исследование? | |
| 7 | Когда найдена причина? | |
| 8 | Когда найден workaround? | |
| 9 | Когда готов фикс? | |
| 10 | Когда решение доставлено клиенту? | |
| 11 | Когда проблема закрыта? | |

## 5. Как быстрее (анализ эффективности)

### Нужные люди
Кого следовало подключить раньше?

### Нужные данные
Каких логов, стендов, проектов или диагностических данных не хватало?

### Автоматизация
Что можно автоматизировать, чтобы обнаружить проблему быстрее?

### Процесс
Какой этап можно сократить или убрать?

## 6. Где ждали (точки ожидания)

Определить точки ожидания и их длительность:

- ожидание данных клиента;
- ожидание ответа ТП;
- ожидание разработки;
- ожидание оборудования или стенда;
- ожидание согласования;
- другие точки ожидания.

Для каждой точки: что стало причиной ожидания и можно ли его сократить.

## 7. Предотвращение повторения

Перечислить конкретные действия по каждой выявленной причине:

| Действие | Ответственный | Срок | Статус |
|---|---|---|---|
| | | | |

Не ограничивайся общими формулировками («улучшить процесс»). Каждое действие должно быть **конкретным и измеримым**.
